# План страницы мониторинга Xray

Дата исследования: 2026-09-06. Начата реализация контрактов и слоя состояния; см. traffic-monitor-architecture.md. Подключение ядра и UI ещё не выполнено.

## Проверенные факты

- Windows / C# / .NET 10 / WinUI 3 / CommunityToolkit.Mvvm. Публикация использует Native AOT и trimming.
- Ядро: Assets/engine/xray.exe, Xray 26.6.1 Custom, Go 1.26.0.
- XrayConfigBuilder.Build сейчас генерирует log, dns, inbounds, outbounds, routing и опционально fakedns. API и сбор статистики не включены.
- XrayService запускает отдельный процесс, получает stdout/stderr, публикует LogReceived и RunningChanged. Буфер журнала ограничен 500 строками.
- LogLineParser умеет только выделять timestamp. Парсера обращений пока нет.
- LogWindow обновляет UI пачками раз в 100 мс; этот подход стоит сохранить.
- Главный экран состоит из двух колонок. PersonalizeHost лениво создаётся в правой колонке. Навигация реализована через _showPersonalize, полноценного переключателя страниц нет.
- Начальный размер окна 950×600; монитор нужно размещать на всю ширину FullModePanel, с компактным вариантом для узкого окна.
- Библиотеки графиков и gRPC в проекте сейчас нет.

## Практическая проверка ядра

Запущен отдельный скрытый процесс из временного каталога, без TUN, системного прокси и пользовательских настроек. Запрос через локальный SOCKS на локальный HTTP-сервер с телом 4096 байт.

Временная конфигурация: stats={}, api.listen=127.0.0.1:<свободный порт>, api.services=[StatsService, RoutingService], policy.system с четырьмя statsInbound/OutboundUplink/Downlink=true.

Команда xray api statsquery вернула:

- inbound>>>probe-in>>>traffic>>>uplink: 72
- inbound>>>probe-in>>>traffic>>>downlink: 4222
- outbound>>>direct>>>traffic>>>uplink: 59
- outbound>>>direct>>>traffic>>>downlink: 4210

Лог: from tcp:127.0.0.1:<порт> accepted tcp:127.0.0.1:<порт> [probe-in >> direct].

Вывод: счётчики работают. Inbound и outbound считают на разных границах; их нельзя складывать, иначе будет двойной учёт. Это объём на уровне ядра, а не точный объём провайдера с накладными расходами туннеля. Тестовые процессы остановлены, временные файлы удалены.

## Ограничения источников

- В protobuf есть SubscribeRoutingStats, но upstream v26.6.1 регистрирует RoutingService с nil-каналом; реализация возвращает Routing statistics not enabled. На нестандартном бинарнике streaming RPC отдельно не проверен. Не закладывать его как рабочую основу.
- StatsService даёт счётчики по inbound/outbound и пользователям ядра. Пользователь Xray не равен приложению Windows.
- Access-событие содержит время, источник, назначение, статус, теги маршрута. Оно не подтверждает успешную доставку или открытое сейчас соединение.
- В обычном access-событии нет PID/имени приложения, байтов конкретного соединения и времени закрытия. Показывать неизвестное значение, не выдумывать.
- Домен и реальный IP одновременно доступны не всегда. Маскирование адресов в логах учитывать; не отключать его скрыто.
- Webhook маршрутов есть в исходниках версии, но требует изменений правил и делает HTTP-запрос на событие. Для первого этапа не нужен; PID в его стандартной схеме также отсутствует.
- TUN, UDP, цепочки и пользовательские правила ещё требуют сценарных проверок на реальном UI.

## Предлагаемая первая версия

Отдельная полноширинная страница «Трафик», кнопка входа из основной панели, возврат на основной экран. Нативные WinUI-контролы в текущей теме.

1. Карточки: загрузка/отдача в байтах в секунду, принято/отправлено за сессию мониторинга, число зарегистрированных обращений.
2. Линейный график загрузки и отдачи за последние 5/15 минут. Опрос раз в секунду; скорость = разница счётчиков / фактически прошедшее время.
3. Разбивка трафика по маршрутам proxy/direct; блокировки показывать количеством событий, а не фиктивными мегабайтами.
4. Таблица «Обращения»: время, назначение, порт, TCP/UDP, источник, маршрут. Поиск, фильтр маршрута, сортировка, копирование адреса, подробности выбранной строки.
5. Топ назначений по количеству обращений, без приписывания им объёма трафика.
6. Пауза останавливает только отображение; сбор продолжается. Очистка сбрасывает локальную историю/базовые значения, а не счётчики ядра.

Не включать в первую версию: достоверный список активных соединений, трафик по приложению/домену, гарантированные имена приложений, URL-пути HTTPS. Последнее зашифровано; первые пункты потребуют дополнительной телеметрии ядра или сопоставления с Windows вне заявленного охвата.

## Реализация по шагам

### 1. Подключить статистику

- XrayConfigBuilder: добавить stats и policy.system, локальный API только со StatsService. Использовать упрощённый api.listen, чтобы API не попадал в пользовательские правила и счётчики.
- XrayService: выбирать порт до генерации конфигурации, передавать endpoint службе мониторинга; обработать занятый порт и смену endpoint при рестарте. Не менять работающий конфиг на диске без контролируемого перезапуска.
- Новый XrayStatsClient: постоянный gRPC-канал через Grpc.Net.Client и сгенерированные protobuf-типы, без запуска xray api каждую секунду. Проверить Native AOT/trimming сразу на минимальном прототипе.
- Считать общий трафик по выбранным пользовательским inbound (mixed-in/tun-in); outbound использовать только для разбивки. Не суммировать звенья цепочки как независимый общий трафик.
- reset=false. При рестарте/уменьшении счётчика сбрасывать baseline скорости, не рисовать отрицательный поток или скачок. При недоступном API показывать «нет данных», не ноль.

### 2. Собирать обращения

- Новый XrayAccessEventParser: типизированные события из LogReceived, отдельный от оформления LogLineParser.
- Обработать IPv4, IPv6, домены, >>/->, accepted/rejected, пользовательские теги, маскированные адреса и неподходящие строки.
- Новый TrafficMonitorService: отдельный ограниченный буфер 5000 событий и 900 точек графика; сбор с начала сессии независимо от открытой страницы.
- Обновление UI пачками каждые 250 мс. Не блокировать обработчик stdout, не передавать ObservableCollection между потоками. Счётчик вытесненных событий при переполнении.
- Отписка, отмена опроса и освобождение канала при остановке/закрытии. Изолировать сбои монитора от работающего прокси.

### 3. Построить страницу

- MainViewModel: заменить boolean навигации на явное состояние Main/Personalize/Traffic.
- MainWindow: ленивый TrafficMonitorHost на всю ширину, сохранить mini mode и кнопку возврата.
- Новые TrafficMonitorViewModel, Views/TrafficMonitorControl.xaml, Controls/TrafficChartControl.
- Для двух линий предложен нативный XAML Path/Polyline, без новой библиотеки графиков. Ограничить число точек; tooltip, шкалы, адаптация к теме и размеру.
- Виртуализированный ListView с колонками, заголовками сортировки и панелью подробностей. Не размещать таблицу в отключающем виртуализацию внешнем ScrollViewer.
- Добавить строки en-US и zh-CN, доступные подписи и управление клавиатурой.

### 4. Проверить

- Unit: парсинг событий, IPv6/маскирование, скорость по монотонному времени, сброс счётчиков, пропуски данных, ограничения буферов и фильтры.
- Интеграция: локальный HTTP/SOCKS через настоящий бинарник, рост/разделение счётчиков, direct/block, рестарт API, занятый порт.
- Отдельно TUN/UDP и chain: отсутствие двойного счёта и неверного направления uplink/downlink.
- UI: 950×600 и узкое окно, обе темы, большой поток событий, переходы Main/Personalize/Traffic/mini, закрытие страницы во время опроса.
- Release publish с Native AOT, а не только Debug build.
